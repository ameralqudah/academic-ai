## 1. Executive summary

Academic AI is a large, carefully built product.
- About 73,000 lines of TypeScript.
- Next.js 16 with React 19, Drizzle ORM and PostgreSQL (26 tables).
- Auth.js v5, the beta release.
- Three LLM providers (Anthropic, OpenAI, Google), called with plain `fetch`.
- Full Arabic and English support.

Some parts are strong enough to build a competitive product on:

- **Classical statistics are trustworthy.** The engine covers t-tests, one-way ANOVA with Welch and Tukey, Pearson and Spearman correlation, OLS and logistic regression, chi-square and Fisher, Mann-Whitney, Wilcoxon, Kruskal-Wallis, Cronbach's α and Shapiro-Wilk. It is deterministic and cross-checked against SciPy to about 1e-10. The LLM never produces a number.
- **The task engine is typed and saved to the database.** Plans are dependency graphs. Budgets, parallel steps, pause/resume, questions to the user and typed step outputs are all implemented.
- **Retrieval is grounded.** Literature comes from Crossref, OpenAlex and Serper. Answers use numbered, closed-set citations. Evidence is extracted first, then synthesised. Deep research runs as a real multi-step pipeline.
- **Arabic and English are handled properly.** Right-to-left layout uses logical CSS properties, fonts are self-hosted, there are 1,326 translation keys with full coverage, and exported Word files are right-to-left.
- **Documents can be generated** as DOCX, PPTX, XLSX, CSV, Markdown, BibTeX and RIS, with versioned artifacts and SVG path diagrams.

It is not yet a professional research platform, and it is not agentic in the sense modern assistants are:

1. **Security (🔴/🟠):**
   - The installed Next.js has a critical remote-code-execution advisory.
   - Any logged-in user can read another user's chat history by sending that conversation's ID.
   - Someone who registers with the owner's email can become admin.
   - Suspending a user or removing admin rights does not revoke sessions.
   - Login has no rate limit.
   - The server can be tricked into fetching internal addresses via redirects and IPv6.
2. **Wrong statistics (🟠):**
   - In PLS-SEM and CB-SEM, blank cells become **0**.
   - CFA standard errors are divided by the number of indicators instead of *N*.
   - CFI and TLI are inflated. For example, the correct CFI of 0.940 is reported as 0.982.
   - HTMT and cross-loadings are computed on misaligned rows.
   - Q² is not the standard blindfolding Q².
   - These results would not survive peer review.
3. **Background work is not durable:**
   - Agent tasks, deep research and PLS bootstrapping start as fire-and-forget promises inside the web process.
   - On Vercel they are frozen once the response is sent.
   - With several instances they can run twice.
   - The bootstrap blocks the Node event loop for 7–47 s, and cancelling it does not work.
4. **It is a workflow engine, not an agent (about 4/10):**
   - Regex-first intent detection, then one LLM call writes a JSON plan.
   - Fixed code dispatches the plan's steps.
   - No native tool calling, no act–observe loop, no critic.
   - No long-term memory, and conversation history is never summarised.
5. **Research is grounded on titles only:**
   - Literature reviews and `document.write` see only `[n] Title (Year)`. Abstracts are dropped.
   - The PDF parser is regex-based, with no OCR.
   - There are no embeddings.
   - In-text `[n]` numbers do not match the alphabetical APA reference list.
6. **The analyses researchers need most are missing:** mediation, moderation, moderated mediation, EFA/KMO/Bartlett, omega, the full CB-SEM structural model, factorial and repeated-measures ANOVA, ANCOVA, and PLSpredict, MGA and IPMA.
7. **The product is fragmented:**
   - There are three chat backends (`/api/chat`, `/api/agent`, `/api/ai/chat`) and two chat UIs.
   - About 600 lines of `agent-chat.tsx` can never run.
   - Four visible chat controls are broken: regenerate, the variable-role picker, the model selector, and editing a message sent in the current session.
   - The sidebar's "Deep Research", "Web Search" and "Literature Review" items only pre-fill text.
8. **Engineering hygiene:**
   - There is no CI.
   - About 690 KB of stale copies are committed in `src/server/context/` (`Smoke · TS`, `Handlers · TS`, …, and a pasted shell command).
   - Many tests check the source code's text rather than its behaviour. The one failing test is one of these.
   - There is no error tracking or tracing.

**Where the advantage lies.** Do not try to beat general assistants at general chat. Win on a **research-integrity pipeline**: one structured *Research Project Graph* linking question → constructs → hypotheses → questionnaire items → dataset columns → verified analysis runs → manuscript sentences → verified citations. Every number and citation in a generated manuscript would be traceable and checked. General assistants do not offer this, and the codebase already has the pieces to start: deterministic statistics, a typed task engine, and a claim/citation quality engine.

**Recommended path:**
- **P0, 3–5 weeks:** fix security, statistics correctness, durable jobs, CI, and the broken chat controls.
- **P1, 2–3 months:** a native tool-calling agent loop, memory with retrieval, abstract/full-text grounding, one citation engine, mediation/moderation/EFA and full SEM, and a project-centred workspace.
- **P2/P3:** the differentiators — traceable manuscripts, journal matching, reviewer response, reproducibility bundles, and university tenancy.

| Stage | What actually happens | Assessment |
|---|---|---|
| **User** | `agent-chat.tsx` `runRouted()` posts `{message, conversationId, projectId, datasetId}`. It does **not** send the selected model, the chosen variable roles, or `regeneratedParentId`. | Three UI controls have no effect |
| **Intent detection** | 1) An order-sensitive keyword regex (`keywords.ts`) returns immediately with confidence 1. 2) A small-talk regex. 3) Otherwise one LLM call picks from 21 intents (`intent.ts:317`). 4) Regex overrides in `router.ts` and `routing-rules.ts`. | Brittle. `/\bpls\b/` sends "pls help me write…" to PLS-SEM. The classifier call is not metered. |
| **Planning** | Fast path: no plan. Agent path: fixed templates for data and diagrams, otherwise one LLM call producing a JSON DAG over 16 capabilities (`planner.ts:295`). The router's suggested capabilities are computed but never passed to the planner. | One-shot planning. The user never sees or approves the plan. |
| **Tools** | Code maps capability IDs to handlers through a registry. No provider-native tool calling. | Tools are chosen once, up front, not step by step. |
| **Execution** | `void planAndRun()` in the web process. Up to 3 steps in parallel. Budgets of 50 steps, 2 hours, 120 model calls. Immediate retries with no backoff. Step timeouts are not enforced (`executor.ts:708`). | Not durable. Duplicates across instances. Breaks on serverless. |

## 5. Weak and unfinished components

### Correctness bugs (results are wrong today)

1. **Blank cells become 0 in SEM.** `Number(null) === 0` in `pls.service.ts:117,313,414,496` and `data-analysis.service.ts:256`. A blank Likert response turns into a real 0.
2. **CFA loading standard errors divide by the number of indicators.** `cfa.ts:675` divides by `Math.sqrt(observed.length)`, the size of the p×p covariance matrix, instead of *N*. The standard errors do not depend on sample size.
3. **CFI/TLI use an approximate null model.** `cfa.ts:615-634`: pairwise −log(1−r²) instead of −(n−1)·log|R|. With 12 items at r = .5, the correct CFI of 0.940 is reported as 0.982.
4. **Other CFA defects:**
   - `df = max(1, …)` hides under-identified models.
   - The residual floor means the Heywood check can never fire.
   - Factor-correlation standard errors use Fisher's formula.
   - The optimiser is a pattern search.
5. **PLS rows are misaligned.** HTMT, formative VIF and cross-loadings use `data.slice(0, estimate.n)` (`assessment.ts:343,353,459,495`): the first *n* raw rows, not the complete cases.
6. **PLS blindfolding Q² is non-standard.** It is close to in-sample R² (`blindfolding.ts:239-290`).
7. **Formative outer VIF** uses the largest pairwise r² instead of the multiple R².
8. **Citation numbers do not match the reference list.** Numeric `[n]` citations are used in the text, while APA sorts the list alphabetically without numbers (`styles.ts:259-279`, `handlers.ts:~1030`).
9. **Thesis chapters are truncated silently.** A chapter is one call capped at about 2,400 tokens (`ai.service.ts:465,504`), with no check of the stop reason.
10. **Anthropic stream errors look like a finished answer.** `anthropic.ts:145-172` ignores the error event, so an interrupted reply is shown as complete.

### Routing and agent bugs

- **Any earlier-work reference turns the task into a document conversion** (`task.service.ts:261-303`). For example, "run a t-test on my data" with a dataset attached: the analysis step is removed.
- **Answering the agent's question can loop.** Most handlers never read `userAnswers`, so they ask the same question again.
- **`continueFrom` is never read.** "Continue the review" rewrites the whole review.
- **Replanned corrective steps get `dependsOn: []`.** Steps that consume their results run first, on the thin sources.
- **Step timeouts are not enforced.** The `AbortController` is created but nothing races against it.
- **Tasks can get stuck.** Tasks left in `QUEUED` or `REPLANNING` are never resumed. `resumeInterrupted` runs on every cold start and can duplicate tasks that are still running.
- **The legacy orchestrator answers from memory.** It marks every capability "available", so PLS or web requests there get a memory answer with no tools.
- **`statistics.pls` cannot run through the task engine.** It needs `pls-model.v1`, which nothing produces. It works only through `/api/pls`.

### Unmetered and unsafe AI paths

- **Unmetered calls:** long-form generation and the intent classifier bypass quotas.
- **Failover can leak the premium model to free users.** `runWithFailover` ignores the plan's allowed list (`ai.service.ts:122`).
- **No fetch timeouts.** Up to three stacked retry layers.
- **Raw provider error bodies (up to 400 characters) reach the client.**
- **The Google API key is sent in the URL query string.**
- **Web-search prompts include fetched page text unfenced**, without being marked as untrusted data (`ai.service.ts:867-904`).

### Duplication and dead code

- **Three chat backends and two chat UIs.** About 600 unreachable lines in `agent-chat.tsx`, which has 20 `useState` hooks and 3 SSE parsers.
- **Two context systems** (`src/ai/context`, `src/server/context`).
- **Four job tables** (`agent_tasks`, `tasks`/`task_steps`, `analysis_jobs`, deep-research jobs).
- **Two reference systems** and **two survey generators**.
- **Two page pairs that duplicate each other:** Wizard vs. Workspace, Proposal vs. Thesis.
- **Unused exports:** `withFailover`, `listProviderNames`, `resolveRequirement`, `unmetRequirements`, `provenanceChain`, `PayloadFor`, `registerCapability`, `summaryForPeriod`, `costByKind`.
- **Committed junk:** `src/server/context/{Ai.service · TS, Analysis, Analysis · TS, Handlers · TS, Language · TS, Long form · TS, Smoke · TS, language.ts.txt}`, about 690 KB.

### Tests

- About 150 assertions `readFile` the source and check substrings. They break on harmless refactors and miss real bugs. The current failure, "only configured providers are candidates", is one of these.
- No test covers the `/api/chat` ownership path or the conversion of blank cells to 0.
- The SEM tests check properties only. None compare against SmartPLS, lavaan or AMOS reference numbers.

### How the components communicate

1. **Request intake.** The browser calls the BFF.
   - The BFF authenticates with a database-checked session and scopes every read by `userId`.
   - It reserves quota atomically.
   - It either answers directly (a short chat turn streamed from the model gateway) or **enqueues a task**, then returns the `taskId`.
2. **Workers.** Workers lease tasks with a heartbeat and run the supervisor loop.
   - Every tool call is a typed function (zod → JSON Schema) that the model calls natively.
   - Each tool result is saved as a `task_step` with provenance.
   - Each event is published to Redis. The BFF forwards those events to the browser over SSE, so there is no database polling.
3. **Sub-agents.** Each sub-agent is the same loop with a narrower tool set, prompt and budget. The supervisor calls a sub-agent as a tool (`delegate.research`, …). Independent sub-agents run in parallel.
4. **Verification.** The verifier runs before any artifact is final.
   - A number in the prose must resolve to an `analysis_run` value.
   - A citation must resolve to a verified reference, and the claim must be supported by that reference's abstract or full text.
   - Failures go back to the writing agent, for up to N rounds. What remains is shown to the user as an integrity report.
5. **Human checkpoints.** A checkpoint pauses the task in `WAITING_FOR_INPUT` with a typed question: plan approval, the model specification for SEM, a destructive data transformation, or final sign-off. Answers are written into the step's input.
6. **Statistics.**
   - Classical tests stay in TypeScript (fast and verified).
   - SEM, EFA, mediation and moderation go to a **sandboxed stats worker** running the established reference libraries: lavaan and semTools for CB-SEM/CFA, seminr for PLS-SEM, psych for EFA and omega, and processR or lavaan for PROCESS models.
   - Every run stores its input hash, library versions and generated script. That makes analyses reproducible and exportable.
7. **Memory.**
   - Each thread keeps a rolling summary.
   - The project memory is a *Research Project Graph*: nodes for question, constructs, hypotheses, items, variables, runs, sections and references.
   - User memory holds degree, field, preferred style and language.
   - Every retrievable item is embedded in pgvector and searched with hybrid lexical + vector search.

## 11. Unique features Academic AI should develop

1. **Research Project Graph.** One typed model: Problem → Questions → Constructs (with definitions and sources) → Hypotheses → Measurement items → Dataset columns → Analysis runs → Results → Manuscript sections → References. Every feature reads from it and writes to it. This is the "research memory" and the moat.
2. **Traceable manuscripts.** Every statistic in the text is a live link to the analysis run that produced it. Every citation is a link to a verified source and the passage that supports the claim. Anything that can't be traced is flagged. Export an **Integrity Report** alongside the manuscript for supervisors and journals.
3. **Methodology advisor with automatic test selection.** Extend `recommend.ts` to explain *why* a test was chosen, citing methodological literature. Examples: Hair et al. for PLS-SEM; Hu & Bentler for fit cut-offs; Hayes for PROCESS.
4. **Construct-to-questionnaire pipeline.** From constructs, propose validated scales found in the literature (with sources), adapt items, handle translation and back-translation (Arabic ↔ English), mark reverse-coded items, and generate the column map for the future dataset. When data arrives, the constructs are already mapped, so PLS/CB-SEM models are built automatically.
5. **One-click SEM from hypotheses.** The hypotheses graph becomes a lavaan or seminr model. The run covers the measurement model (reliability, validity, HTMT with CIs), then the structural model (paths, R², f², Q²predict, mediation). Results come back as APA/SmartPLS-style tables, a figure, and an interpretation paragraph whose every number is linked.
6. **Automatic interpretation.** Results sections follow reporting guidelines (APA JARS; Hair et al. PLS reporting). Limitations are generated from the actual assumption-check results.
7. **Literature engine.** Snowballing through OpenAlex and Semantic Scholar citation graphs. Elicit-style evidence tables (method, sample, constructs, findings). Gap maps (construct × context × method). A consensus summary for each hypothesis.
8. **Citation and source integrity.** DOI resolution (Crossref and DataCite), retraction checks, predatory-journal signals, a claim-support score per citation, and a "cited but not read" warning.
9. **Journal matching and submission kit.** Match the manuscript to journals using OpenAlex venue data (scope similarity, open-access status, typical time to publication, indexing). Apply the chosen journal's template. Generate a cover letter, highlights, a graphical-abstract outline, and a reviewer-response letter with a point-by-point table that links changes to manuscript diffs.
10. **Reproducibility bundle.** Export a zip with the cleaned data, a codebook, R/Python scripts that reproduce every run, library versions and a data-transformation log.
11. **Supervisor and university mode.** Share a project with a supervisor (comment only). Institution formatting templates, including Jordanian and Gulf university thesis rules. Seat-based university licensing and SSO.
12. **Arabic-first academic writing.** Arabic academic register, bilingual abstracts, Arabic PDF/LaTeX output with correct shaping, and transliterated references handled by the CSL engine.
13. **Research project management.** Milestones: proposal → ethics → data collection → analysis → defence. An inbox of agent tasks waiting for input, and progress tracking tied to the graph.

## 13. Recommended development order

1. **Sprint 0 (week 1): safety.** P0-1 dependency upgrades, P0-2 IDOR fix, P0-4 rate limits, P0-12 stray-file removal and CI skeleton, P0-14 Sentry. Nothing else ships until CI is green.
2. **Sprint 1 (weeks 2–3): trust.**
   - P0-3 auth hardening.
   - P0-7 statistics correctness, with reference-value tests against lavaan/seminr.
   - P0-11 citation numbering.
   - P0-8 chat controls.
   - P0-5 SSRF and upload hardening.
   - P0-13 production configuration.
3. **Sprint 2 (weeks 4–5): reliability.**
   - P0-6 queue and worker, with the bootstrap moved off the event loop.
   - P0-9 AI-layer safety.
   - P0-10 routing bugs.
   - Then **P1-1**: consolidate to one agent stack. This removes most of the ambiguity before new work starts.
4. **Phase A (months 2–3): agentic core.**
   - P1-2 native tool calling, then P1-3 supervisor, verifier and plan approval.
   - P1-4 memory and P1-14 event streaming in parallel.
5. **Phase B (months 2–4, in parallel with A if two engineers): research-grade.**
   - P1-5 retrieval, then P1-8 grounded writing, then P1-9 citation engine, then P1-10 live quality checks.
   - P1-6 stats worker, then P1-7 data preparation, then P2-4, P2-6 and P2-5.
6. **Phase C (months 3–4): experience.** P1-11 information architecture, P1-12 frontend refactor, P1-13 GDPR.
7. **Phase D (months 5–7): the moat.** P2-1 Research Project Graph, then P2-2 traceable manuscripts, then P2-11, P2-8 and P2-10. Alongside: P2-3 and P2-7.
8. **Phase E (month 8+):** the P3 items, driven by university customers.

**Why this order:**
- Correctness and security issues put users' theses at risk today.
- The durable worker is a prerequisite for every agentic feature.
- Consolidating the stack first avoids building the new agent on top of three competing paths.
- The Research Project Graph is most valuable once memory, citations and statistics already produce trustworthy, typed data to link together.
